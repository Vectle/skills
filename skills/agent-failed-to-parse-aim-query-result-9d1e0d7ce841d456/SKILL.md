[vjovanov (closed issue)] ## What is wanted Let authors write a local section component and derive its full canonical address from the document hierarchy, rather than repeat the parent path at every depth. Today the README's login example contains: ```markdown # FS-login: Login ## format: Formatting ### format.1: Username Trim surrounding whitespace. ``` The child should not need to repeat `format`, while citations and query results continue to use `FS-login.format.1`. The exact unambiguous authoring syntax must be specified before implementation; this is not a request to silently reinterpret existing `### 1` headings. **Owner direction:** explicitly approved pursuing this feature and revisiting the full-path requirement on 2026-10-12. The request is wanted, not awaiting approval of its general direction. ## Why the contract cannot express it today [FS-config.3.3.1](https://github.com/agent-grounds/grund/blob/main/docs/functional-spec/FS-config.md) requires complete paths at every depth. The prior named-sections decision deliberately chose explicit paths; current behavior is correct under that contract. This proposal revisits that choice. Strict depth checks and query rendering must be specified in terms of resolved canonical coordinates where appropriate. ## What it would change for existing callers Existing explicit headings and citations must retain their meanings and validity. Introduce an unambiguous new form or explicit opt-in/versioned adoption, with defined parent selection, mixed explicit/relative documents, collisions, missing parents, and ambiguity errors. Moves and renames must not silently retarget citations. The scanner, check, show, refs, formatter, completion, and LSP must agree on the canonical address. Triage measured 8 citation sites across 5 files for FS-config.3.3.1; the impact extends beyond parsing to those shared-map consumers. Acceptance: a runnable nested login example resolves to `FS-login.format.1` without repeating `format` in the child heading; old documents retain their addresses and verdicts; move/rename behavior is tested; the README teaches the accepted syntax. Evaluate deep nesting as well, keeping Markdown's H6 ceiling a separate constraint rather than requiring a beyond-H6 extension. ## Alternatives Keep explicit paths: deterministic but repeats more ancestry at each level. Flatten headings: reduces repetition by losing useful structure. Automatically reinterpret existing numeric headings: rejected because it changes existing meanings. Relative authoring with full canonical output preserves self-contained citations without requiring authors to duplicate ancestry. ## Why it is worth it Repeated ancestry adds authoring work and another consistency obligation, particularly in deeply nested specifications. Removing it supports friendliness-first and the principle that Grund maintains the knowledge structure. Full canonical addresses preserve precise agent grounding and broken-reference checks. Shorter headings alone are not claimed to reduce retrieval-token costs. Origin: local report `grund.24`; triage classified this as a foundational product change, with the prior-policy conflict explicitly accepted for pursuit by the owner.
