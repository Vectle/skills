Short answer: align the two sides. Either upgrade the library doing the import to a release that no longer imports HybridCache, or pin transformers back to a late 4.x that still exports it. Changing your own import is not an option when the failing import is inside a dependency. ``` ImportError: cannot import name 'HybridCache' from 'transformers' ``` 1. Read the traceback to the frame that imports HybridCache and note which package it is (commonly peft, reached through diffusers). That package and transformers are the pair to align. Expected: you can name both packages. 2. Check installed versions: `python -m pip show transformers peft diffusers`. Expected: transformers is 5.x (or older than the HybridCache window) alongside a peft/diffusers release built against 4.x. 3. Preferred fix, move forward: `python -m pip install --upgrade peft diffusers transformers` so the importer is a release written for the new cache API. Verify with the import that failed. Expected: the application starts. 4. Pin-back fix, when upgrading the importer is not possible: `python -m pip install "transformers[torch]"` with a late 4.x version constraint (for example the 4.48 to 4.52 range), then restart the process or kernel. Expected: `python -c "from transformers import HybridCache"` succeeds. Record the pin with a comment; it is technical debt that blocks future transformers upgrades. 5. If your own code imports HybridCache, migrate it: build the cache through the model's generate path or the DynamicCache family in current transformers instead of constructing HybridCache directly. Root cause: a hard import of a removed public name. transformers removed HybridCache in the 5.x cache rework, and any dependency that imports it at module load fails instantly, before any of your code runs, which is why the traceback points into site-packages. When to use: startup import failures where the traceback ends at a transformers import of HybridCache inside peft, diffusers, or a pipeline package. When NOT to use: a similar error naming a different cache class in your own script is your code to update, not a version pin. In hosted notebook environments, install and then restart the kernel; the old transformers stays loaded otherwise. Variant phrasings: "importerror cannot import name hybridcache from transformers peft", "diffusers hybridcache import error", "photomaker hybridcache transformers". Edge cases: mixed conda and pip installs can leave two transformers versions where pip show and the interpreter disagree; check `python -c "import transformers; print(transformers.__file__)"`. Pinning transformers down can break a different dependency that already requires 5.x; resolve the set together with pip's resolver rather than forcing one package.

Context: HybridCache was a key-value cache class exported by Hugging Face transformers during part of the 4.x line, used for models mixing attention types. It was removed in transformers 5.x as the cache API was reworked, and it also does not exist in transformers versions older than the release that added it. The import error almost never comes from your own code: a downstream library (peft and diffusers chains are the usual path) still does `from transformers import HybridCache`, so the crash surfaces deep inside an import chain at startup when the installed transformers is on the wrong side of that window.
